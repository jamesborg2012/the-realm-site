## Workflow

- One item = one session = direct commits to master (no PR / branch).
- At the start of each session, Claude reads this file and **asks for a brief** on the chosen item before implementing — items below are names only.
- Items move: `Backlog` → `In Progress` (with brief) → `Done` (with commit SHA + 1-line outcome) or `Dropped` (with reason).
- Cross-cutting decisions that should bind future work go to Claude memory, not here.

- [x] **12. Order total VAT bug** — orders showed an order total with **no VAT** (total = ex-VAT subtotal) in two situations. **(a) Admin-created orders (the main cause):** staff create orders via **Orders → Add Order**, add line items, and save without pressing **Recalculate** — so WC saves the line totals from the posted fields but never computes per-line tax from the rates, storing the order with no VAT. Pressing Recalculate (or applying a voucher, which triggers a recalc) was masking it. Fix: recalc taxes + totals automatically, but **only on the initial create**, not on every save (an every-save recalc was prototyped then dropped as too heavy). Two hooks on `woocommerce_process_shop_order_meta`: `capture_admin_order_pre_save_status` (prio 5) records whether the order is still an `auto-draft` *before* WC updates its status at prio 40; `recalculate_new_admin_order_totals` (prio 60, after WC saves line items at 45) then calls `$order->calculate_totals(true)` + `save()` only when that flag is set — so it fires once per newly-created order and never on later edits (which still need the Recalculate button, by design). Recomputes taxes via `WC_Order::get_tax_location()`, which falls back to the store base country for address-less orders; HPOS-safe via `wc_get_order()`; status detection avoids relying on form fields so it works under both HPOS and the legacy posts table. **(b) Frontend countryless orders (belt-and-braces):** item 3 made `billing_country` optional, so a guest can check out with no country; WC's cart tax uses `WC_Customer::get_taxable_address()`, which returns the empty country verbatim, so the MT-specific VAT rate never matches. Fix: `TRM_WC_Hooks::default_taxable_address_to_base` on `woocommerce_customer_taxable_address` (prio 99) substitutes the store base country/state/postcode/city (Malta) when the resolved taxable country is empty. Both fixes leave orders that already carry a country (members, future non-MT orders) untouched — Malta-only until other countries are handled. No template/JS changes.

- [x] **6. Pre-Order handling** — new self-contained `TRM_Preorder` class (`classes/preorder/trm-preorder.php`, extends `TRM_Core`, required + instantiated in `functions.php` right after `TRM_Coming_Soon`, which it depends on). **"Pre-order" = Coming Soon category:** a product is a pre-order while it carries the `trm_coming_soon_category` term (or a descendant), via `TRM_Preorder::is_preorder_product()` → `has_term()` against the category id + `get_term_children()`; variations resolve to the parent id (`category_post_id()`). Because detection is purely category membership, once `TRM_Coming_Soon`'s daily cron strips the category on the release date the product silently becomes normal and none of the rules below apply — satisfying "limit not considered after release" with zero extra code. **Per-product limit:** a `_trm_preorder_limit` number field on the **Inventory** tab (`woocommerce_product_options_inventory_product_data` / saved on `woocommerce_process_product_meta`); empty meta = no limit (`get_limit()` returns `null`). Alongside it a **read-only "Pre-Orders Placed"** display (own id `trm_preorder_ordered_count_display`, never saved) shows the live count. **Order-count tracking:** `_trm_preorder_ordered_count` product meta is the live pre-ordered quantity. A single idempotent `reconcile_order()` (via `sync_order_count()`) recomputes each pre-order line's contribution and applies only the delta, so the overlapping hooks can't double-count. Target contribution per line = 0 when the order is in a non-counting status (`cancelled`/`refunded`/`failed`/`trash`), else `(ordered_qty − refunded_qty)` clamped at 0. Hooked on `woocommerce_checkout_order_processed` (storefront), `woocommerce_order_status_changed` (admin orders + every transition, incl. restoring from cancelled), `woocommerce_order_refunded` (**partial AND full refunds** — a partial doesn't change status, so this is its only signal; reduces the count by the refunded qty per line) and `woocommerce_refund_deleted` (deleting a refund restores the qty). `woocommerce_new_order` is deliberately NOT hooked — it can fire mid-construction before line items attach and would count an empty order. Which lines are tracked is remembered on the item (`_trm_preorder_counted_product_id`) the first time it's seen as a pre-order line, and the currently-applied qty on `_trm_preorder_applied_qty`; after that the category is never re-checked, so reversal stays exact even once the product leaves the category on release. All meta R/W via `$order`/`$item` CRUD methods → HPOS-safe; counts clamp at 0. **Cart isolation + limit enforcement:** `woocommerce_add_to_cart_validation` (blocks adding a pre-order item to a cart with normal items and vice-versa; blocks adding beyond `limit − already_ordered − in_cart_qty`, matching same-product variations by parent id) and a whole-cart re-check on `woocommerce_check_cart_items` (catches quantity edits / stale carts — mixing reported first, then per-product over-limit). Both no-op when no Coming Soon category is configured. **Checkout notice:** `woocommerce_review_order_after_order_total` → renders a `<tr class="trm-preorder-row"><td colspan="2"><div class="trm-preorder-notice">…</div></td></tr>` beneath the order total, only when the cart holds a pre-order item; text editable via a new **"The Realm — Pre-Orders"** section under **WC → Settings → General** (`woocommerce_general_settings`, option `trm_preorder_payment_message`, default "Payment is required before your pre-order can be confirmed."). **Styling:** new SCSS partial `assets/scss/preorder.scss` (`@use`d in `styles.scss`, recompiled to `layout.css`) — amber bordered box mirroring the On Order notice; `.trm-preorder-row td` strips inherited tfoot cell padding/border. No template edits — all wired via existing hooks.

CRON to remove coming soon category when expired** — new self-contained `TRM_Coming_Soon` class (`classes/coming-soon/trm-coming-soon.php`, extends `TRM_Core`, required + instantiated in `functions.php`). **Setting:** new "The Realm — Coming Soon" section under **WC → Settings → General** (via `woocommerce_general_settings`) with a `wc-enhanced-select` dropdown of all `product_cat` terms, stored in option `trm_coming_soon_category` (term ID; empty = feature disabled). Static helper `TRM_Coming_Soon::get_category_id()` reads it. **Release date field:** a Meta Box "Release Information" panel on the product editor (`rwmb_meta_boxes`) with one `date` field `trm_release_date` (saves `Y-m-d`), `js_options.minDate => 0` so only today-onward is selectable — mirrors the realm-events-manager `event_date` convention. **Single-product display:** `woocommerce_single_product_summary` priority 11 (right after the price at 10) renders an italic `<p class="trm-release-date">` — only when the product is in the Coming Soon category; shows the localised release date, or "Release date: To Be Announced" when unset; nothing for non-Coming-Soon products. **Catalog logic:** `pre_get_posts` (prio 99) adds a `product_cat NOT IN [coming soon]` (`include_children`) tax clause to frontend product listings, so Coming Soon products are hidden from other category archives, the main shop, and search — listing only on the Coming Soon archive itself (detected via the `product_cat` query var, incl. descendants). Skips admin/AJAX/REST and single product pages (direct URLs still work). The header live-search query in `TRM_WC_Hooks::handle_live_search` (AJAX, so not covered by `pre_get_posts`) got the same exclusion via the `TRM_Coming_Soon::get_category_id()` helper. **Cron:** `maybe_schedule_cron` (on `after_setup_theme`) registers a daily `trm_remove_coming_soon_expired` event pinned to ~00:01 site-local time (`wp_timezone()` + `DateTime::getTimestamp()` for the UTC epoch WP-Cron wants); the handler `remove_expired_coming_soon` finds matching products with a single direct `$wpdb` query (posts ⋈ term_relationships ⋈ term_taxonomy ⋈ postmeta) — published products carrying the Coming Soon term whose `trm_release_date` is non-empty and `<= today`. The date compare is a **lexicographic string** comparison on the stored `Y-m-d` value (chronological for ISO dates), deliberately avoiding MySQL `CAST(... AS DATE)` which silently yields NULL/no-match if the value isn't a clean date — this was why the earlier `WP_Query`/`wc_get_products` `meta_query` (`type => 'DATE'`) and the `wc_get_products` `category`-by-slug attempts returned nothing. The join is on `term_taxonomy_id` mapped to the configured `term_id`. Category removal still goes through `wp_remove_object_terms()` (not raw SQL) so term counts/caches stay consistent. Uses `<= today` not `== today` so a missed run on a quiet site (WP-Cron is traffic-triggered) self-heals next time. `clear_cron` unschedules on `switch_theme`. **Note:** WP-Cron fires on the first request after the scheduled time, so exact 00:01 firing depends on traffic; a real OS cron hitting `wp-cron.php` can be added later for precision without code changes.
